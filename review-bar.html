Review bar

Built into every inlined prototype. Reviewers comment on elements, retype copy in place and spotlight a region, all without touching the code. Comments land in a feedback.json next to the prototype, ready for a coding agent to apply.

Enable it

Every prototype shows a small circle button in the bottom-right corner. Click it and the bar appears at the bottom centre; click it again to turn the bar off. The choice is remembered for that page. The same works from the URL: ?review=1 turns it on, ?review=0 off. Until someone turns it on, the prototype renders clean apart from the button, which is what shared and deployed links show.

https://opz-prototypes.vercel.app/action-trace/?review=1

ModeWhat it does
Interact IUse the prototype normally. The bar stays out of the way.
Edit text EHover highlights any text; click it and retype. Enter saves, Esc cancels. Edits are stored by element path and reapplied whenever the prototype re-renders, so they survive navigation inside the page. The bar shows an edit counter with an undo-all button.
Comment CHover outlines elements; click one and type a note in the side panel (⌘↵ posts). A numbered pin marks the element. The panel lists Open / Resolved / All with Resolve, Delete and “Go to” when the prototype reports screens.
Spotlight SDrag a rectangle and everything outside it is dimmed, for screenshots and walkthroughs. A plain click or Esc clears it.

Esc always steps back: it clears a spotlight first, then returns to Interact.

Shared with everyone

Comments and text edits are not private. The bar sends every change to a small store at /api/feedback and polls it every few seconds, so anyone who opens the same prototype sees the same pins, the same comments and the same edited copy, and sees new ones appear while the page is open. The first time you post you are asked for your name; it is shown on your comments and edits. The status at the right end of the bar reads Shared when the store is reachable and Local only when it is not, in which case everything stays in that browser.

Locally

The Icarus dev server is the store. It writes each prototype's feedback to feedback.json next to its index.html.

node tools/serve.mjs /absolute/path/to/features 5733

For the Claude Code preview panel, the matching .claude/launch.json entry is:

{ "name": "features", "runtimeExecutable": "node", "runtimeArgs": ["/abs/path/designmd/tools/serve.mjs", "/abs/path/features", "5733"], "port": 5733 }

On Vercel

Deployed prototypes need a hosted store, set up once per Vercel project:

  1. Copy tools/vercel-api-feedback.js to api/feedback.js in the repository Vercel deploys. Vercel turns api/*.js into a serverless function on its own. No package.json or build step.
  2. Add a Redis database from the Vercel Marketplace. Vercel → the project → Storage → Create Database → Upstash Redis (the free plan is plenty) → connect it to the project. This injects KV_REST_API_URL and KV_REST_API_TOKEN.
  3. Redeploy. The bar switches from "Local only" to "Shared" on the live link. Until the database is connected the function answers 503 and the bar keeps working locally.

Anyone with the link can read and write comments; there is no login. Fine for a prototype review link shared inside the team, not for anything public.

Hand the comments to an agent

Two ways, same result.

  1. Say “apply the prototype comments” in a Claude Code session on the prototype folder. It reads the store (feedback.json locally, or GET /api/feedback?p=/the-prototype/ on the live site), implements every comment with resolved: false in index.html, then marks each one resolved: true with a one-line resolution. Resolved comments turn green in everyone's panel.
  2. Or press “Copy comments as prompt” in the side panel. The open comments land on the clipboard as plain text for any other agent or a chat window.
Apply these prototype comments in action-trace/index.html: #1 [Screen 3 · ROB · Action Trace added] button.btn "Create token" → Move this to the far left of the header #2 [Screen 3 · ROB · Action Trace added] h3 "Supplier Invoice Management" → Shorter title please

Inline text edits are applied at runtime and are not baked into the source unless you ask for it.

The document

One document per prototype, the same shape in feedback.json and from the API. edits is keyed by element path plus text-node index; comments is a list. Writes are small operations (POST /api/feedback with { p, ops }: upsert a comment, delete one, set or clear an edit) so several reviewers never overwrite each other. The operations are listed in tools/feedback-store.mjs.

{ "edits": { "layer:init/1.0.0.0#0": { "orig": "Supplier Invoice Management", "text": "Supplier invoices", "screen": "Screen 3 · ROB · Action Trace added", "author": "Roman" } }, "comments": [ { "id": "cmg…", "n": 1, "path": "layer:init/1.0.0.0", "el": "h3 \"Supplier Invoice Management\"", "html": "<h3>Supplier Invoice Management</h3>", "screen": "Screen 3 · ROB · Action Trace added", "screenId": 3, "url": "/action-trace/", "rect": { "x": 532, "y": 24, "w": 240, "h": 24 }, "text": "Shorter title please", "author": "Roman", "created": "2026-10-08T12:47:00.000Z", "resolved": false } ] }

el is a human label, html the first 600 characters of the element's markup, screen whatever the prototype reports as the current screen, falling back to the page title. Together they are enough for an agent to find the spot in the source.

Nothing to wire up

inline.py bakes review.css and review.js into every prototype it touches, next to the design-system CSS. For a prototype that doesn't use the system CSS at all, inject just the bar:

python3 inline.py --only-review ../features/my-feature/index.html

Both forms are idempotent: re-running refreshes the bar in place.

Optional host adapter

A prototype with its own screen or flow model can tell the bar about it by defining window.REVIEW before the bar loads. Everything is optional; without it comments carry the page title and elements are addressed relative to the direct children of <body>.

window.REVIEW = { api: '/api/feedback', // where the store lives (default) screen: () => ({ id: state.step, name: SCREENS[state.step] }), // stamped on every comment goto: id => showStep(id), // enables "Go to" on a comment roots: '[data-layer], #main, .sidenav', // stable containers for element paths key: el => el.id === 'main' ? 'main:' + state.page : null, // name a container whose content changes };

Pins and edits are matched by container plus child-index path. If a prototype swaps a container's whole content depending on state, give that state a name through key so a comment left on one page doesn't resurface on another.
