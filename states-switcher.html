States switcher

A floating panel in the bottom-left corner of a prototype that jumps between its designed states: default, empty, loading, error, long text, each step of a flow. Hidden until the page is opened with ?states=1, so shared links stay clean. A prototype convention, copied into each prototype that needs it.

Enable it

Open any prototype that carries the switcher with ?states=1 and the panel appears bottom-left. Click a state to show it; the current one is outlined in the accent colour. The – button in the header collapses the panel to its title bar, and that choice is remembered for the session. Without the parameter the panel is not rendered at all.

https://opz-prototypes.vercel.app/initiatives/?states=1

Each state also has a direct link. Add &state=<key> to land on it straight away, which is how states are shared, screenshotted or compared side by side. The keys are the data-state values listed below.

https://opz-prototypes.vercel.app/initiatives/?states=1&state=create-errors

The switcher and the review bar are independent and stack: ?states=1&review=1 lets a reviewer comment on a specific state.

The panel is 232px wide, dark title bar, white body, buttons grouped under small uppercase labels. It sits bottom-left on purpose: the drawers, modals and side panels it drives open on the right, and the plugin launcher owns the bottom-right corner. How it works

Three parts live in the prototype's index.html, each under the prototype's own class prefix (in-, tt-, pr-, ig-, imp-): a block of CSS, the panel markup with one data-state button per state, and a script with a STATES map keyed by those same names. The script does nothing unless ?states=1 is in the URL, then reveals the panel, wires the buttons and runs the entry for ?state= (or default).

There are two ways a state gets produced, and prototypes pick whichever fits:

ApproachHow a click worksUsed by
Reload and replay The button sets ?states=1&state=<key> and reloads. On load the state's entry drives the real UI step by step: opens the drawer, types into fields, picks from selects, clicks Create. Every state therefore starts from a clean page and exercises the real code paths, which keeps it honest as the prototype evolves. Initiatives, Initiatives full screen
In-page re-render The button swaps the content region without reloading: either by re-rendering from data (TopTrack sets loading / error / empty flags and re-renders the dashboard) or by swapping in markup kept in <template> elements (Integrations v3, CSV export, Performance reviews). Fast, and the markup for each state is captured once rather than rebuilt by script. TopTrack, Integrations v3, CSV export, Performance reviews

A state can be kept but hidden from the panel by commenting its button out. It stays reachable through &state=<key>, which is what Initiatives does for empty, no-results and long-text.

Add it to a prototype

  1. Pick a prefix.Use the prototype's existing class prefix so the switcher's CSS cannot collide with the design system or another prototype's inlined block.
  2. Paste the three blocks below.CSS into the prototype's own <style> (not the design-system block, which inline.py rewrites), the panel markup at the end of <body>, the script after it.
  3. Add one button and one STATES entry per designed state.Keep the key identical in both places. Group buttons by screen or flow step. Cover the states the system asks for: empty, loading, error, at scale, long text.
  4. Make each state reproducible.Drive the real UI (click, type, pick) or re-render from data; avoid hand-editing DOM into a shape the prototype could never reach on its own.
  5. Mention it on the feature's card.Reviewers only find the panel if they know about ?states=1. Link the most useful states directly with &state=.
