Plugin launcher

One button, bottom right of every prototype, that owns all the author plugins. Before it, each plugin had grown its own trigger in its own corner — and the component map had none at all outside the kit — so there was no way to tell what a page even carried.

What it looks like

Plugins
Review barComment, retype copy, spotlight a region. States switcherJump between this prototype's designed states. Component mapOnly on the component kit for now. VersionsOnly on features prototyped in versions. ChangesOnly on a version that marks its changes.
Switching one reloads the page, so it starts clean.
1

The badge counts what is running. A plugin the page does not carry is listed greyed out with the reason rather than hidden, so the panel is an honest inventory — you can tell at a glance whether a prototype has states defined, or whether the bar simply has not been inlined yet.

What it switches

PluginParameterDetected by
Review bar?review=1review.js announcing itself, or the bar it leaves behind.
States switcher?states=1An element whose id ends -switcher containing [data-state] buttons.
Component map?map=1The kit's goggles button, or a page that ships the registry.
Versions?versions=1<meta name="icarus-versions"> in the page head (a versioned feature).
Changes?changes=1The same meta tag, plus at least one [data-change] marker.

Detection is structural rather than a flag each plugin sets, so prototypes built long before the launcher still light up correctly without being edited. The states check looks for [data-state] on purpose: switchers are hand-copied with a per-prototype prefix (in-, pr-, tt-, …) so there is no common class, and a product-level control like the workspace switcher would otherwise be mistaken for one.

Why it reloads

Each plugin decides what to do at boot — stamp the page, replay a state, render a bar. Flipping one live would mean three teardown paths that only ever run in author tooling, so the launcher reloads instead: one path, and the page always starts in a known state.

It always writes an explicit =1 or =0 rather than deleting the parameter, because the plugins disagree about what a missing one means — the review bar remembers its last state in localStorage, so it needs a literal review=0 to be told to stop. Everything else in the URL, the hash and any &state= included, is carried across.

Nothing to wire up

inline.py carries plugins.css and plugins.js into every prototype alongside the review bar, inside the same markers, so refreshing an existing prototype picks the launcher up in place:

python3 inline.py --only-review ../features/my-feature/index.html

A prototype that carries the review bar gets the launcher automatically. One that does not — because it was never inlined — gets neither; run the command above and it gets both.
